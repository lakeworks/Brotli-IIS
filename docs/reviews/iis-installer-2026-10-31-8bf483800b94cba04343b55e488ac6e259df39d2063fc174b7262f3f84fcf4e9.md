### [O1] Full-revert path omits WWW restart after an activated install

`Get-UndoText` (`install-iis.ps1:157-161`) gives two recovery paths. Soft restore ends with `Restart-Service W3SVC -Force` so workers reload the previous DLL. Full revert is labelled “instead” and is only:

```text
& '…\appcmd.exe' restore backup 'brotli-iis-…'
```

No restart follows. The mid-move warning at `:149` and the missing-DLL warning at `:153` both send the operator to that full-revert line.

After a successful install with `-RestartWww`, workers already hold the new DLL. Restoring `applicationHost.config` alone leaves them on that image until WWW restarts. Microsoft documents that scheme `dll` / level changes take effect only after a WWW service restart ([scheme reference](https://learn.microsoft.com/en-us/iis/configuration/system.webserver/httpcompression/scheme/)); `CLAUDE.md:42` states the same. Soft undo teaches that rule; full revert, now the prescribed answer for the failure modes the note itself calls out, does not.

For a mid-move failure before any restart, config restore alone is enough. For undo after an activated install, the printed full-revert commands leave workers on the new DLL. Add the same restart step (or an explicit “restart if the new DLL was already loaded”) under the full-revert stanza.

### [P1] Mid-move warning is printed when `br` was already first

When the previous `br` was first, install updates attributes in one commit (`install-iis.ps1:121-124`) and never removes the scheme. `Get-UndoText` still always emits the remove/re-add mid-move warning (`:149`) whenever any prior `br` existed. Gate that comment on `-not $Br.First` so upgrades of an already-first `br` do not describe a failure window that path cannot create.
